# Plan: 0.4.0

Four things ship. The first finishes something that already runs and has never been published; the
second makes the loot system answer to a server owner rather than only to a pack author; the third
finishes cloth, which shipped in 0.3.0 knowing it stopped at the waist and saying so; the fourth
makes what a part *does* something an author can shape, which today it very nearly is not — ninety
of the ninety-one parts have no behaviour at all.

They are independent, and the order below is the order to build them in. The web editor is a second
repository and touches no Java. The loot work is Java and data with no client half, and it comes
second because the content pack later in this document stands on it. Cloth is client rendering and
one tag, and it wants the most looking at. Effects come fourth because their authoring surface is
generated out of the Java by a tool the Blockbench plugin reads, so they are cheapest to land once
section 1 has settled.

Beyond them, three sections sketch the line after 0.4.0 at roadmap depth: the part website, the
animation system, and the mob-loot content pack. Those get plan files of their own when their turn
comes. The animation section is the exception — it makes the architectural decision now, because
that decision changes what the Blockbench plugin has to be able to author, and the plugin is being
worked on in section 1.

## 1. The web editor, finished and published

*The `blockbench plugin port` item. Work in progress in `C:\Users\Matthijs\ArmorPiecesBlockbench`.*

### Today

The port works. `ArmorPiecesBlockbench` is at `dcd171f`, two commits, and it does what its README
claims: a pinned Blockbench 5.1.6 web build serving the desktop plugin, with `require('fs')` backed
by Pyodide's virtual filesystem holding the mod's own pack, and the repository's real Python running
under Pyodide for the rigs, the geometry conversion, the ramps, the effect schema and the skin bake.
Browsing all 91 parts, opening one on the posed figure, painting the master and the static and mask
sheets, the Part dialog, the recipe controls, the skin workspace and Save all work. A start page of
its own replaces Blockbench's, so a visitor arrives at the parts rather than at a format list.

Two test suites exist and pass: `test:python` runs every tool under Pyodide and against the real
repository and compares stdout byte for byte, and round-trips `bb_geo` over all 91 parts;
`test:browser` drives the built site in Chromium through `window.armorpieces_api`.

The plugin is not forked. `build/make_plugin.mjs` makes exactly three edits to the desktop file and
**throws if any pattern stops matching**, which is the mechanism that keeps one source of truth.

### What is missing

Everything that is missing is publication, not function.

- **There is no remote.** `git remote -v` is empty; nothing is pushed; Pages is not enabled. The
  editor exists on one laptop.
- **There is no CI, and there is a reason it is possible anyway.** CI cannot build `web/repo.tar.gz`
  or `web/armorpieces.js` — they need `tools/.mcassets` and the Minecraft jar. That is exactly why
  both are committed. So CI's job is the part it *can* do: `npm run blockbench` (clone the pinned
  tag, build the web target) and `npm run site`, then publish `dist/site`. Both test suites run in
  CI as well — `test:python` needs only Pyodide, and `test:browser` needs only Playwright and the
  built site.
- **Nothing records which Armor Pieces commit the bundle is a snapshot of.** `repo.tar.gz` and
  `web/armorpieces.js` are the mod at some moment, and there is no way to tell from the repository
  which moment, nor any check that fires when they go stale. This is the one real correctness risk
  in the whole port: a plugin built from a moved desktop file will fail the build loudly, but a
  *pack* built from a stale clone fails silently and shows the wrong parts.

### What changes

1. **Push it.** Create `mattjesmc/ArmorPiecesBlockbench`, push `main`, enable Pages.
2. **A workflow.** `npm ci && npm run blockbench && npm run site && npm test`, publishing
   `dist/site` to Pages on green. `vendor/` stays uncommitted and is cloned by the workflow, which
   is also what keeps the GPL boundary honest — the modification stays the two lines
   `make_site.mjs` writes into `index.html`.
3. **Stamp the bundle.** `make_bundle.py` writes the source clone's `git describe --always --dirty`
   and its commit date into `bundle.json`, the start page shows it in the footer beside the version,
   and the bundler **refuses a dirty clone** unless forced. A demo built from uncommitted work is
   fine to make and not fine to publish without knowing.
4. **Verify the load-from-URL claim once.** The README tells a reader to load `dist/armorpieces.js`
   into `web.blockbench.net` by URL. That path is not covered by `test:browser`, which drives our
   own site. Do it by hand once against the published URL, and if it works, add it to
   `test:browser` as a second target so it stays working.
5. **Say what the tab boundary is.** Edits live in the virtual filesystem and last as long as the
   tab. That is the correct answer for a demo and the wrong answer for section 5, so the start page
   should say it plainly, and `export_pack.py` — which already runs there — is the seam the website
   will use rather than a new one.

Explicitly **not** in 0.4.0: accounts, storage, sharing, or anything that survives a refresh. Those
are section 5 and they need a decision that has not been made.

### Check

- The workflow builds from a clean checkout with no local `.mcassets`, and both suites pass in it.
- The published URL opens the start page, opens a part, paints it, and saves it, in Chrome, Firefox
  and on a phone-width viewport.
- The footer names the Armor Pieces commit; bumping the mod and re-running `npm run bundle` changes
  it; a dirty clone is refused.
- `vendor/` is absent from the repository and Blockbench's `LICENSE.MD` is present in `dist/site`.

## 2. Loot, answerable to a server

*Loose by intent. This section fixes the shape of the problem and the direction of the answer; the
exact config schema and command grammar are settled when it is built.*

### Today

Four families — parts, skins, cloths and fitting templates — reach the world through one mechanism.
`DecorationLootTables` listens on `LootTableEvents.MODIFY` and, for each table as it loads, adds **one
pool, rolled once, with one `random_chance` on the pool**. Two routes feed that pool: a `loot` list
on the thing's own data file, which is exact, and a `LootGroup` file, which is a category of tables
naming a tag of members. Six groups ship. Where several sources name one table the highest chance
wins, and a member offered twice is one entry at its best weight.

That design is right and nothing here changes it. The chance belongs to the table, so a
ninety-second part changes which part is found and never how often, and a chest never holds two of
ours. Everything below has to preserve both properties.

Three things are also already true and are worth saying because they narrow the work:

- **Modded tables already work.** The event fires for every table id the game loads, ours, vanilla's
  and any mod's alike. A group naming `somemod:chests/whatever` works today with no code.
- **A foreign table can already hand out our items.** `minecraft:set_components` with
  `armorpieces:decoration` on an `armorpieces:brow_template` is documented in the 0.3.0 plan and
  needs nothing from us.
- **Java is doing this precisely because a datapack cannot.** A pack can replace a vanilla table but
  never add to one, and two packs replacing `chests/ancient_city` cannot both win.

### What is actually missing

1. **A server owner has to author a datapack.** Groups are pack data — correctly, because they are
   content. But "make parts rarer on my server" should not require making a datapack, and today it
   does. Note that `ArmorPiecesConfig` is client-only *by explicit design* and says in its own
   javadoc that a server-side setting needs its own file and its own load point. This is that
   setting, and it gets that file.
2. **Nothing is discoverable.** There is no way to ask the game which loot tables exist, which of
   them the mod touched, or at what odds. For vanilla tables you can look them up; for a modded pack
   the ids are unguessable, which makes "inject into any modded container" true in principle and
   unusable in practice.
3. **The reverse direction is exact-only.** A foreign table can name *a* part, by id. It cannot say
   "a random knightly one", and a table naming a part that is not installed is a hard failure rather
   than a skipped entry — which makes a modpack's loot table brittle against a pack the player did
   not install.
4. **Some mods do not use loot tables at all.** A mod that fills a chest from code is out of reach
   of this or any other datapack-shaped mechanism. Say so in the docs rather than implying otherwise.

### The direction

- **A server file.** `config/armorpieces-server.json`, its own file and its own load point,
  reloadable. It does not replace groups; it **overrides** them, keyed by group id — chance, weight,
  and tables added or removed. Pack authors keep authoring content; server owners tune it. A global
  multiplier over everything is probably the one knob most people actually want, and is cheap.
- **Commands, which are mostly the answer to (2).** A `/armorpieces loot` subtree: list the loaded
  table ids with a filter, explain what the mod added to one table and why (which group, at which
  chance, how many members), and dry-roll a table *n* times and print what came out. `explain` is
  the one that turns a modded pack from unusable into usable.
- **A loot entry type of our own**, so a foreign table writes one entry and gets a member of a tag
  rather than a named part — and an absent member is skipped, not fatal. This is the honest answer
  to "modded loot containers can reference our items added by packs": the reference should be to a
  *tag*, because a tag survives the referenced part not being installed.
- **`set_decoration` gains the same tag form**, for the rarer case of finding decorated armor rather
  than a template.

### Check

- The one-pool-per-table invariant survives every route: a table reached by a group, an override and
  a foreign entry at once still yields one pool and one roll.
- An override in the config beats the group file; removing the override restores it; `/reload` picks
  both up.
- A foreign table naming a tag with nothing installed logs once and drops the entry.
- `explain` on a vanilla chest and on a modded one both name the group and the chance actually used.

## 3. Cloth past the waist

### Today

Two cloths ship, tunic and tabard, and both stop at the waist. That was deliberate and the cloth
plan argues it at length: a texture can only paint texels some box of its own item samples, and a
chestplate's layer draws the torso and the two arms and nothing over the thigh. A leggings hem was
built, read cleanly at three to five rows, and was cut for three reasons — it is a second smithing
operation on a second item, it makes "half-wearing a garment" reachable, and the leg boxes swing
apart so a long hem splits down the middle at every step.

The capability was left in place rather than removed: a `humanoid_leggings.png` beside the mask is
already read as a hem, `#armorpieces:clothable_armor` ships chest armor only, and
`SmithingClothRecipe` already accepts leg armor. So a pack can have a hem today by editing one tag.

### What changes, and it is four things

**One garment, read from the chest slot.** The reason the hem was cut is that it was a second
component on a second item. The fix is not to make the player do two operations — it is to stop the
leggings from owning the decision. A cloth is a property of the outfit, so when the leggings layer
is painted the mixin reads `armorpieces:cloth` off the **chest** slot's stack and bakes the hem from
that. One smithing operation, one component, one garment, and "half-wearing" stops being reachable
because there is nothing to half-wear. The cost is a new rule to state: a player wearing a tabard
and no leggings has no geometry under the waist and gets no hem, which is the same rule the feature
already has one layer up. Leg armor stays out of `clothable_armor` — it is not what carries the
cloth any more, so it should not be craftable onto it.

**The backside gets the base colour.** Each leg box has six faces with their own texel rects on the
vanilla sheet, so the inner and rear faces of a hem are texels nobody has painted. Unpainted is a
hole. They take the **base colour alone, shaded** — never the pattern, which is what the existing
mask rule already says for everywhere that is not one of the two torso panels, extended to the leg
boxes' faces. This is what makes a hem read as a garment seen from behind rather than as a decal
that vanishes when the player turns. *Assumption worth confirming: this is what "background-colour
painted backside" meant. If it meant the back of the torso panel instead, that is already the
tabard's `chest.back` panel, which is drawn from the pattern's north face by design.*

**The inflation step.** A leg box inflates 0.4 where the chest box inflates 1.0, so a hem is
visually thinner than the garment above it and there is a visible ledge at the waist. Two ways out:
accept the step and cut the mask so the join lands on a fold, or lift the hem's rows onto a matched
inflation. Try the first; it costs nothing and may be enough at Minecraft's texel size.

**A hem length that survives walking.** The legs are two boxes that swing apart, and no bake can fix
that. Cap the mask's reach to the rows that read at a full stride, and let the two cloths ship
different lengths so the limit is visible rather than implied. A garment that genuinely *hangs* is
geometry — that is a part, `scale_skirt` already is one, and it belongs with section 6 rather
than here, because a hanging garment that does not move is worse than one that does not hang.

And the follow-up the cloth plan left open, which belongs here because it is the same file: **cloth
on the advanced smithing table**, at place 1 of the piece's own row beside the trim and the skin.
The row is already the piece's own, `MAX_FITTINGS` is already 3, and the widest socket row already
draws three columns, so the box does not change size.

### Check

- A tunic and a tabard on iron, gold, diamond, netherite and leather, dyed and undyed, plain banner
  and six-layer banner, with and without leggings, at rest and mid-stride.
- The same outfit skinned: the skin's form comes through the hem as it does through the chest.
- Turn a full circle: no unpainted face, no pattern on the hem, no seam at the waist that reads as
  an error rather than as a hem.
- Leggings alone, no chestplate: no hem, no log spam, no crash.
- Take the chest cloth off: the hem goes with it in one operation.
- `/reload` twice while worn, to see the LRU released and rebuilt.

## 4. Effects an author can shape

### Today

Behaviour is the one half of a part that is not data. `DecorationEffect` is a dispatched codec over
a registry of `MapCodec`s — vanilla's own shape, the same one enchantment entity effects use — so a
mod registers an effect type in its initializer and from that moment anyone's datapack can name it
on a part. Five hooks, closed on purpose because a hook is a moment in the server loop this mod
actually reaches: `Ticking`, `Damage`, `Attributes`, `Gliding`, `Lifecycle`. Five effect types, open
on purpose: `attribute`, `mob_effect`, `blink`, `glide`, `if_fitting`.

The authoring surface already exists too. `tools/effect_schema.py` **parses the Java records** —
their `MapCodec` field list, their bounds, their defaults and the `@param` lines beside them — and
the Blockbench plugin builds a control per field out of that. So a field added to an effect appears
in the editor for free, *provided* its codec is one of the shapes that parser recognises. Anything
else is reported as `unknown` and shown read-only. That is the binding constraint on everything
below: a new field shape is not done until `effect_schema.py` can read it.

And one number says what this section is for. **One part out of ninety-one carries an effect** —
`pinions`, with `armorpieces:glide`. The system was built, documented, and then almost never used.

### The two examples, measured against that

**Feather boots that jump further already work today, with no code and no new anything.** 26.2's
attribute registry holds `jump_strength`, `safe_fall_distance`, `fall_damage_multiplier`, `gravity`,
`air_drag_modifier` and `bounciness`, among about thirty others, and `armorpieces:attribute` takes
any of them:

```json
{ "type": "armorpieces:attribute", "id": "armorpieces:heel_wings_jump",
  "attribute": "minecraft:jump_strength", "amount": 0.15, "operation": "add_multiplied_base" }
```

So what that example exposes is not a missing capability. It is that nothing ships using it, nothing
tells an author the list exists, and no number in it can be looked at or tuned without editing a
file. That is a content and a discoverability problem, and it is most of the work in this section.

**Claws that hit harder are half there, and the missing half is the interesting one.**
`minecraft:attack_damage` through the same effect is a claw that hits harder with everything, which
is one line of JSON. *With hands* — unarmed, or holding a particular thing — has nowhere to live,
for two separate reasons:

- **The only condition that exists tests the part, not the wearer.** `if_fitting` wraps any effect
  in a `FittingPredicate`, which asks what is set in the part's own fittings — the gem in the
  circlet. There is no way to ask about the wearer at all: what they hold, what else they wear,
  where they are, what they are doing.
- **`Attributes` is required to be a pure function of the part**, because the dispatcher applies
  modifiers on equipment change and then leaves them in place until the next one. A modifier that
  depended on the main hand would go stale on the next hotbar key — and silently, because
  `onEquipmentChange` returns early on any slot that is not one of the four armor slots, so a
  main-hand swap does not even reach the reconcile.

**And there is one moment the hook set genuinely does not reach.** `Damage` is damage aimed *at* the
wearer. Nothing sees damage the wearer *deals*. That is a real hole rather than a missing
convenience — and it is worth knowing before planning around it that Fabric API 5.0.5 offers
`ALLOW_DAMAGE`, `AFTER_DAMAGE`, `ALLOW_DEATH`, `AFTER_DEATH` and nothing else: **there is no
damage-modification event to hook.** `ALLOW_DAMAGE` is a veto and can only refuse a hit, never
enlarge one.

### What changes

**A wearer predicate, in two tiers — and the tiering is the design.** The reason to split it is the
purity rule above, which is real and should not be quietly broken.

- **Equipment-shaped conditions** — what is in the hands, what else is worn — become legal on
  `Attributes`, by widening the reconcile rather than weakening the rule. `EQUIPMENT_CHANGE` already
  fires for the hand slots; the dispatcher ignores them. Let a main- or off-hand change re-run the
  armor slots' attribute reconcile, and the rule becomes *a pure function of the part and the
  wearer's equipment* — still pure, still reconciled at every moment it can change, and the claw
  falls straight out of it with vanilla's own damage formula doing the arithmetic.
- **Everything else** — position, dimension, weather, health, sneaking, sprinting — is legal on
  `Ticking`, `Damage`, `Gliding` and `Lifecycle`, and **refused at load on `Attributes`**, with a
  message that says why. Silently stale is the failure mode the purity rule exists to prevent, so
  the file should not load rather than half-work.

Shape it as `armorpieces:if`, taking **vanilla's own entity predicate** rather than a condition
language of ours — the same argument `AttributeEffect` already makes for spelling its fields exactly
as vanilla spells them. It buys held items, worn equipment, effects, dimension, block underfoot,
weather, time and the entity flags in one move, and an author already knows the syntax from
advancements and loot tables. `if_fitting` stays as it is; the two nest, because `ConditionalEffect`
already wraps any effect including another condition.

**Values that scale with the material.** `DecorationEffectContext.material()` exists, and its own
javadoc says it is why the whole entry is carried rather than just the part — "a netherite plume
that dodges more often than an iron one is a single lookup, with no second registry entry and no
second part". Nothing uses it. Give the numeric fields a scaled form: a bare number as now, or a map
from material or tag of materials to a number with a default. One netherite claw and one iron claw
stop being two parts, and a material a pack invents tomorrow is covered by the tag it joins. This is
the piece with the `effect_schema.py` cost attached — it is a new codec shape, and every field that
takes it goes read-only in Blockbench until the parser learns it.

**An outgoing-damage hook, once — and deliberately not by mixin.** With the equipment tier above,
the claw does not need one, and that is the recommendation: build the tiered predicate first and see
what is still unreachable. If something is, the hook is `AFTER_DAMAGE` dispatched over the
*attacker's* worn parts, which can answer a blow but not resize it. Resizing needs a mixin into the
damage path, and the dispatcher's own javadoc argues at length that every hook here is a Fabric
event rather than a mixin so that a decoration effect cannot break an unrelated mod by winning a
race for an injection point. Breaking that for a damage number is not worth it; say so in the plan
rather than leaving it as an open door.

**Content, and two ways to see it.** The point of all of the above is that ninety parts do nothing.
Pick a modest set where the behaviour is legible from the name — claws, heel wings, greaves, gorget,
quiver, horns — and give them effects, scaled by material now that they can be. Then make them
visible: the part's tooltip should say what it contributes, and `/armorpieces effects [player]`
should print what is worn, which socket it is in, and what each piece is actually adding. Tuning the
numbers server-side belongs in section 2's config file, not in a second one of its own.

### Check

- An `armorpieces:if` on a non-equipment condition wrapped around an `Attributes` effect is refused
  at load, and the message names the effect and the reason.
- The equipment tier holds across a hotbar swap, a death, a relog and an armor stand: the modifier
  appears and disappears at the right moments and never leaks a stale one. Check the attribute is
  gone with `/attribute` after unequipping, not just that the damage number looks right.
- The same part in two sockets, both scaling on material, contributes two modifiers that stack —
  the socket-scoped id rule still holds.
- `effect_schema.py` emits a control for every new field; nothing in the Part dialog reads
  `unknown`, and the dialog round-trips every new shape without loss.
- A world with no effectful parts still does no per-tick work: the tracked-wearer set stays empty.

### As built

Three departures from the sketch above, each for a reason worth keeping:

- **The condition is `armorpieces:if_wearer`, not `armorpieces:if`.** It pairs with `if_fitting` —
  one asks about the part, the other about the person — and "if" alone would have been the vaguer of
  two things in the same list and the same dialog.
- **A wearer condition over a GLIDER is refused as well**, which the sketch did not foresee. Vanilla
  asks `canGlide` on the client, an entity predicate needs a server level, and a gated glider would
  have answered "no" on the client and never taken off. `if_fitting` is unaffected — a fitting is in
  the component the client already holds — and stays the way to gate a glider.
- **No outgoing-damage hook, and the content stays deliberately thin.** The equipment tier reaches
  the claw, so nothing needed `AFTER_DAMAGE`; and rather than give a modest set of parts effects,
  **six parts carry one each, one per mechanism** — an equipment condition with a per-material number,
  a world condition, a bare scaled attribute, a fitting gate, a dodge, a glider. The point of the
  section was that the system was unused and unexplained, and the answer to that is worked examples,
  not more gameplay. What the mod ships is still, on purpose, cosmetic.

## The line after 0.4.0

Sketches. Each gets its own plan file before it is built.

### 5. The part website, and servers that enforce a library

Section 1 gives this its foundation: a hosted editor that runs the real toolchain. What it does not
give it is anything that survives a refresh, and that is the whole distance between a demo and a
website. In order of how much has to be decided:

- **Persistence and identity.** A stored pack per user needs storage and accounts, which is the
  first thing in this project that cannot be a static site on Pages. Worth considering whether
  GitHub itself is the backend — sign in with GitHub, a pack is a repository, sharing is a link,
  publishing is a release — because it removes accounts, storage and moderation in one move and
  matches how the toolchain already thinks about packs.
- **Sharing and a library.** A part or a skin is already a small, self-contained set of files. The
  unit of sharing should be the pack that `export_pack.py` writes, not a new format.
- **Server enforcement.** A server saying "these packs" already exists in vanilla: the server
  resource pack push. The honest route is a server-side manifest plus that mechanism, not a new
  protocol — and the datapack half is the thing that has to arrive with it, which is the part
  vanilla does *not* push. That is the real design problem in this item, and it should be looked at
  before any of the website work, because if it has no good answer the library is a single-player
  feature.

### 6. Animation

**Decide it as pose-driven state tracks, authored in Blockbench, with a physics chain as a later,
optional, client-only addition on top.** Reasons, in the order that matters:

- **Parts already animate for free and nothing should break that.** Each part is drawn in the local
  frame of the humanoid part its socket names — "the parent part's own pose is the animation". A
  crest already rides a turning head. Anything added is *secondary* motion over that frame, not a
  replacement for it, which rules out any design that wants to own the bone.
- **The toolchain principle decides the rest.** Every other thing in this mod is authored in
  Blockbench, written to data, and checked by a Python tool that the plugin and the game both agree
  with. A keyframed track has all three: a timeline to author it in, a field to store it in, a check
  that can read it. A Verlet chain has none — no authoring artifact, no file to diff, and no check
  that can say a part is wrong before it ships. It would be the first part of the mod whose
  behaviour lives only in Java.
- **Physics is still worth having, and it can come second precisely because it is client-only.** No
  data change, no sync, no pack format bump: a `physics` block on a named bone, off by default,
  added in a later release without invalidating a single authored part. Staging it this way means
  the risky half cannot delay the useful half.

Traps to write down now, because they shape the data format:

- **What drives a track.** Walk, run, sneak, swim, elytra, fall, idle — but the render state is what
  the layer actually has, so whatever drives it must be on `HumanoidRenderState` or put there.
  Velocity and a tick counter are the two things nothing currently carries.
- **Mirrored sockets.** Horns, pauldrons, vambraces, tassets, knees, spurs and greaves are modelled
  one side and mirrored by the game. A mirrored track has to mirror too, and the sign convention is
  exactly the kind of thing that is easy to get wrong invisibly.
- **The first-person hand.** Arm parts draw there behind a config, with a different pose stack.
- **`bb_geo` has to carry animation**, and today it carries geometry. That is the largest single
  piece of plugin work in the whole roadmap, and it is why this decision belongs in a document
  written while section 1 is open.
- **Blending.** Two tracks at once (running *and* falling) needs a weight rule, and "last one wins"
  will look broken the first time a player jumps while running.

### 7. Mob parts — a content pack

Cheap on purpose, and it sits on section 2, which is why the loot work comes first. Antlers off the
warden, mob masks from mob heads, goat horns, animal ears, a villager's nose, a floating blaze rod.
Shipped as a **separate pack** rather than in the base mod, which is also the first real test of
whether a pack can join the loot system from outside without editing a file of ours.

Two things to check early rather than late:

- **Mob drops are loot tables**, so the group system already reaches them with no code. Trading is
  not — villager trades are not a loot table, and a part offered by a wandering trader needs a
  different mechanism. Find out which before promising it.
- **A floating, animated blaze rod needs section 6.** Everything else in the list is a static part
  and can ship whenever. Do not let one animated item hold the pack.

## What 0.4.0 is not

No Minecraft version bump is implied; `gradle.properties` stays at 26.2 unless one lands first. No
new template family — parts, trims, skins and cloths remain the four things that can be said about
a piece of armor. No new parts: the 91 that shipped in 0.3.0 are the content of this release, and
the work is in what a server does with them and what a garment can reach.
