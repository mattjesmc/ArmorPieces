# Plan: 0.4.0

Two things carried over from 0.3.0, neither of them a feature. The first is a word: the mod page now
calls the thing on a socket a **piece**, and the game and the repository still call it a **part**.
The second is the short list of gaps 0.3.0 shipped with, each one found and written down rather than
fixed. Nothing here changes what the mod does; both are about what it says and what it admits to.

## 1. The word, everywhere else

`51d227c` renamed every "part" on the mod page to "piece", because the mod is called Armor Pieces and
a reader met both words in the first paragraph. That rename stopped at `modpage.yml` and the three
pages it generates. Three places still say "part", and they are not equal.

**The four strings a player reads.** These are the ones that matter, and they are one edit to
`assets/armorpieces/lang/en_us.json`:

    commands.armorpieces.stage.no_fittings          "...no part declares a fitting that any item fills"
    item.armorpieces.fitting_template.applies_to    "Armor wearing a part with a fitting"
    item.armorpieces.fitting_template.applies_to.named  "Armor wearing a part with a %s"
    container.armorpieces.advanced_smithing.remove.hint "Take the selected part, fitting, trim, ..."

Two of them sit on an item tooltip and one under the button that takes things off, so a player who
read the page then plays the game currently meets both words. This is a language file and nothing
else - no code, no data, no compatibility question. It should simply happen.

**Whether the code follows is the real decision, and it is not obviously yes.** The code's own word
is neither "part" nor "piece" but **decoration**, and it is load-bearing in places a rename cannot
reach without breaking packs:

- `data/<ns>/armorpieces/armor_decoration/<name>.json` - the datapack directory every pack that
  exists writes into, and the registry id behind it;
- the `armorpieces:decoration` and `armorpieces:decorations` item components, which are written into
  every decorated armor item already in every world;
- `armorpieces:set_decoration`, the loot function a pack's own table may already call;
- `ArmorDecoration`, `DecorationAnchor`, `DecorationEntry`, the `decoration/` package;
- `tools/decoration_masters/`, `check_part.py`, `paint_<part>_master.py`, `sync_decoration_masters.py`
  and the Blockbench plugin's own vocabulary.

Renaming the first three is a breaking change for packs and for saved items, and it buys a player
nothing: none of those names is ever shown. The recommendation is therefore **prose and player
strings move; data and code do not**. "Piece" becomes the word the mod says out loud, "decoration"
stays the word the mod is written in, and the authoring guide gets one paragraph saying so, because
an author reads both. If that is accepted, the code half of this section is a single sentence of
documentation rather than a refactor.

**The developer docs are the long tail.** `CHANGELOG.md` (83 uses) and `docs/authoring.md` (103),
plus `docs/plans/`, the briefs under `docs/plans/briefs/`, `.claude/agents/*.md` and
`tools/mcp/README.md`. The changelog's older entries are a record of what was written at the time
and are probably best left alone; the authoring guide is read by people the mod page just taught to
say "piece", so it is the one that should follow. Do it in one pass, with the code identifiers left
literal - that is the same rule the mod page's rename used, and `paint_<part>_master.py` is still
spelled the way the tree spells it.

## 2. The gaps 0.3.0 shipped with

All five are verified as of the 0.3.0 tag, none is a regression, and each has been reported at least
once without being taken.

**`check_part --all` exits 1 on four pieces.**

- `bandolier` has four real problems - the master and the model disagree by 80 opaque px, four
  `over_*.south` faces render as holes, and static and inlay pixels fall outside the silhouette. Its
  painter is stale as well (9 cubes in the model against the painter's 6): the rework in `5f19a37`
  changed geometry and sheets together and left the two disagreeing. This one is a fix, not a
  decision.
- `great_helm`'s two are accepted and documented in `e370686`.
- `feathering` (3 unpainted crest faces) and `mittens` (`main[1].west`) predate 0.2.0, and nobody has
  ever written down whether the cuts are deliberate. Either write that down and let the checker read
  it, or paint the faces.

`antlers`' painter is stale too, but its sheets are right, so that one is script rot and nothing a
player can see.

**`tools/skin_masters/gothic_strict/` is an orphan.** A master pair and a brief with no `armor_skin`
file and no shipped textures, so `check_skin --all` counts fifteen skins where fourteen ship. Either
finish it or delete it.

**The mod's item tags carry no translations.** Fabric's dev log says so on every server start, and a
recipe viewer shows `#armorpieces:clothable_armor` as a raw id to a player looking at the cloth
recipe. Six tags, six lang keys.

**`/armorpieces stage loot` undercounts.** `StageCommand.lootKey` classifies only items carrying
`DECORATION` or `DECORATIONS`, so skin, cloth and fitting templates fall into "everything else" - and
they do drop: 100 rolls of `chests/stronghold_crossing` on the 0.3.0 jar gave 8 piece templates, 2
skin templates and 1 fitting template, of which the report itemised only the first eight. It is a
development command, so this is a reporting bug rather than a shipped one, but it means the loot
tuning that was done against those numbers only ever saw one of the four families.

## Not decided yet

What else 0.4.0 carries. Nothing above is a feature, and the content line and the mechanics line have
both been quiet since 0.3.0 went out.
