# Plan: 0.3.0

Five things, on the `next-templates` branch. The first three are about how a player comes by a part
and its fittings - found, crafted or not crafted, and with which template. The fourth is about where
an author's own work lives. The fifth is a block: a table that shows a piece of armor with everything
it wears and lets the player take a part off again, which the smithing table cannot. Each section
says what the code does today, what changes, what the Blockbench plugin shows for it, and how it is
checked before it ships. The order below is the order to build them in: the two small ones first,
then the template split they both touch, then the pack work, which is plugin-only and can overlap
with anything. The table is code-only and independent of the other four.

## 1. Loot tables for parts

*Landed 2026-09-03, both steps. One deviation from the text below: `chance` is required rather
than defaulted, because under one-pool-per-table a row without it puts the part in every chest.
The mod page paragraph waits for the end of the phase with the rest.*

**Today.** A template carries its part as the `armorpieces:decoration` component, so a vanilla loot
entry can already hand one out with no code:

```json
{ "type": "minecraft:item", "name": "armorpieces:brow_template",
  "functions": [{ "function": "minecraft:set_components",
                  "components": { "armorpieces:decoration": "armorpieces:circlet" } }] }
```

What is missing is the other half of that sentence. Nothing shipped is ever found - every part is
crafted from paper and one item - and a pack that wants its part in a vanilla chest cannot get it
there: a datapack can only replace `chests/ancient_city` whole, and two packs that both do so fight
over the file. The mod is the one place that can *add* to a loot table, through Fabric's
`LootTableEvents.MODIFY`, and it does not.

**Change.** An optional `loot` list on the part's data file:

```json
"loot": [
  { "table": "minecraft:chests/ancient_city", "weight": 5 },
  { "table": "minecraft:chests/bastion_treasure", "weight": 2, "chance": 0.5 }
]
```

On loot-table load the mod walks every part in the `armor_decoration` registry and adds one pool
per named table: one roll, an entry per part that names the table, at the part's weight, with a
`set_components` function on that part's socket template. `chance` becomes a `random_chance`
condition on the entry. A part that names no table is exactly as it is now. The shipped parts each
get one or two tables that fit them - wings in end cities, horns in bastions, the circlet in ancient
cities - at weights low enough that the tables are not rewritten by it.

The one thing to verify first: that `LootTableEvents.MODIFY` runs after the dynamic registries are
loaded, on world start and on `/reload` both, so the part registry is there to walk. If it does not,
the loot half reads its own copy of the part files instead of the registry, which is the same data
read twice and is not the end of the world.

A second step, after the first works: a loot *function* `armorpieces:set_decoration` that puts a
decorated piece of armor into a table rather than a template - a helmet already wearing a gold
circlet with an emerald in it. `SmithingFittingRecipe.applyFitting` is static and public for exactly
this, and `DecorationEntry` already knows how to build the component; the function is a codec over
socket, part, material and fittings, and nothing else. Worth doing because "found a helmet wearing
something" is the moment the mod is for, and it is small once the first step exists.

**Blockbench.** A *Loot* group on the Part dialog: rows of table, weight and chance, with the table
id autocompleting from the game jar (`vanilla_assets.py --list-loot-tables`, the same trick as
`--list-ids`). Save writes the list into the data file or removes the field when the list is empty.

**Check.** `/armorpieces stage loot <table> [rolls]` rolls the table the given number of times and
prints what came out, with a count per part, so a weight can be judged without opening a thousand
chests. Round trip in `check_authoring.py` covers the new field like the others.

**Docs.** A *Found in the world* paragraph under Features and a *Loot* subsection in the authoring
guide, both halves.

## 2. Disabling recipes

**Today.** Every part's template recipe is its own file, and so are the apply recipe per socket and
the two fitting recipes. A pack that wants a part to be loot-only, or a server that wants no fittings
at all, has no clean way to say so: a datapack cannot delete a file the mod ships, and overriding it
with something that fails to load is a log full of errors and a recipe that may still show up.

**Change.** A recipe type that loads and does nothing: `armorpieces:disabled`. It has no fields,
never matches, and has no display, so it is absent from the recipe book and from any recipe viewer
that reads displays. A pack disables a recipe by overriding its file:

```json
{ "type": "armorpieces:disabled" }
```

That is the vanilla way of doing anything to a shipped file, it works on every recipe the mod has -
template, apply, fitting, clear - and it needs no new field anywhere else. The codec ignores fields
it does not know, which is what makes the plugin's half of this cheap.

**Blockbench.** A *Craftable* switch beside the two recipe item fields. Off, Save writes the file
with the type swapped to `armorpieces:disabled` and *everything else kept* - pattern, key, result -
so the choices survive; on, it swaps the type back and the recipe is exactly what it was.
`readRecipe` learns to read a disabled file so the two item fields still show what the recipe was.
The summary line under the buttons says "not craftable" when it is off.

**Check.** A disabled template recipe in a scratch pack: `/recipe give` reports it exists, the
crafting grid does nothing with its ingredients, and the recipe book has no entry. `check_authoring`
round-trips a disabled file byte-identical. Together with section 1 this is the "found, not made"
part, which is the combination to test end to end: disable a part's recipe, give it a loot table,
roll it on the stage.

**Docs.** One paragraph in the authoring guide's *By hand* section, and the recipe-type list on the
mod page gains the type.

## 3. One template per fitting

*Landed 2026-09-03. Two deviations from the text below: the recipe files are
`fitting_template_<fitting>.json`, not `template_<fitting>.json`, because a part and a fitting may
share a name and `template_banner.json` already is the banner part's; and the centre items are an
amethyst block, a copper ingot, any dye and a loom, since an amethyst shard, an iron ingot and a
white banner are already part recipes' centres. The bare template's recipe is gone.*

**Today.** One `fitting_template`, and the item in the third slot decides which fitting it fills.
The Javadoc on `FittingTemplateItem` and `SmithingFittingRecipe` makes the case for that - it keeps
the fitting list open, a pack's new fitting is reachable the moment a part lists it - and the case
still holds. What it costs is discoverability and identity: the recipe book shows one grey template
taking "anything", a pack cannot make a banner template harder to come by than a dye one, and a
template that means gemstones cannot look like one.

**Change.** Templates become per fitting the way socket templates are per part: one item, one
component. `fitting_template` gains an optional `armorpieces:fitting` component naming a fitting id,
and the item model selects its look by it (the `minecraft:select` property on a component, four
textures for the four shipped fittings, the plain one as fallback). That is the pattern the socket
templates already use with `armorpieces:decoration`, and it means a pack that defines a `plume`
fitting gets a plume template by writing a recipe with the component - still no Java.

Routing keeps the item-decides rule but narrows it: with a fitting named, only that fitting on each
part is offered the item. With no fitting named, everything is as today. So the bare template stays
the universal one, existing worlds holding it keep working, and the clearing recipe stays one file:
a named template with an empty third slot empties only its fitting, the bare one empties all.

Recipe files: `template_fitting.json` becomes four, `template_gemstone`, `template_guard`,
`template_inlay`, `template_banner`, each with its component in the result and its own centre item
(an amethyst shard, an ingot, a dye, a banner). `apply_fitting.json` and `clear_fitting.json` stay
one file each, because a template ingredient matches the item regardless of component. The creative
tab lists the four named templates and the bare one.

Tooltip: "Applies to: armor with a Gemstone" from the fitting's `description`, and "Ingredients:" from
a new optional `ingredients` text on the fitting file, with a default per type - a material fitting
says its tag's name, a dye fitting says "Any dye", a banner fitting says "A banner".

**Blockbench.** The New Fitting dialog writes the template recipe as well as the definition, with
the same two item fields the part recipe has. The material preview's fitting dropdowns are
unchanged. `gen_template_icons.py` renders the four textures from the socket template art with a
fitting glyph.

**Check.** Four template recipes render on the mod page (modpage already draws the fitting recipes).
On the stage: a gemstone template plus a ruby onto a sash does nothing, onto a circlet fills the
stone; a bare template still routes everything; a named template with an empty slot clears one
fitting and leaves the other. `/recipe give` loads all four. An armor piece decorated under 0.2.0
reads back unchanged, since no component on the armor itself changes.

**Docs.** The fitting sections of the mod page and the authoring guide; the "thirteenth template
item" wording goes. The Javadoc on the two classes is rewritten to say why the narrowing is a
component and not four items.

## 4. Where an author's pack lives

*Landed 2026-09-03. One deviation: New Pack... makes one half at a time (a datapack or a resource
pack), since one `pack.mcmeta` carries one format and the two halves' formats differ; a folder used
for both is still found and written to as before. Checked live through the MCP bridge: a
`mypack:circlet` split over two scratch folders was found with the halves paired, opened with its
texture and name read from the resource pack, and saved with the geometry and language line
written there and nothing written into the datapack's `assets/`; `check_authoring.py <dp> <rp>`
round-trips it.*

**Today.** The plugin is built around this repository. It needs the repo root to run the Python
tools, and it finds packs in exactly three places under it: `src/main/resources`, every folder in
`run/resourcepacks`, and every `datapacks/*` under `run/saves`. A new piece is written with both
halves in one folder. Masters are looked up by bare part name in `tools/decoration_masters`, so a
user's `circlet` would silently edit the mod's master instead of their file. Language lines go
under `assets/` of the one folder the piece was found in, which is right only while both halves
share a folder.

A user making their own content has none of that: a resource pack under
`.minecraft/resourcepacks/<name>` and a datapack under `.minecraft/saves/<world>/datapacks/<name>`,
two folders, and no repository. What is needed is for the content to stop having to live here,
while the tools still do.

**Change.**

- *The repo is the toolkit, not the workspace.* It stays required - the rigs, the preview, the
  effect schema and the vanilla-asset extraction are Python and are not being ported - but the
  settings page and the first-run error say so: clone it, point the setting at it, install Pillow.
  Content never has to be inside it.
- *Packs are a list the user owns.* A *Packs...* dialog on the panel adds and removes folders,
  stored in a plugin setting as JSON. Discovery is that list plus the repo's three places when a
  repo is configured, plus the running game's own folders when they exist:
  `%APPDATA%\.minecraft\resourcepacks\*` and `saves\*\datapacks\*`, the Mac and Linux equivalents.
- *A piece has two packs.* `pieceRecord` grows `dataPack` and `assetPack`; discovery pairs the two
  halves of a `namespace:name` across every root, and the label shows both when they differ. The
  New Piece dialog asks for a datapack and a resource pack, defaulting to the same folder. Every
  writer goes to the right half: the data file, fittings, recipes and tags to the datapack, the
  geometry, textures and the language file to the resource pack. The language file is the one
  most likely to land in the wrong place, since it is written today wherever the data file is.
- *Masters are namespaced.* Only `armorpieces:` pieces have a master in this repo; anyone else's
  piece edits its own file, which the code already half does. The lookup checks the namespace.
- *New Pack...* writes a folder with `pack.mcmeta` for either half, at the formats in
  `gradle.properties` (88 and 107 for 26.2), so a user does not have to know the numbers. *Export
  Pack...* zips a pack for handing round; the datapack and resourcepack zips the build makes are the
  model.
- *The game loop is documented.* Textures and geometry pick up on F3+T; a data change to a part is a
  dynamic-registry change and needs the world left and re-entered, which is the thing every author
  trips on once.

**Check.** A piece created from the plugin into two folders under a scratch `.minecraft`, never
touching the repo: it shows on the stage, its template crafts, its lang line reads, and
`check_authoring.py --pack <dir>` round-trips it. Reopening the repo's own pieces changes nothing
about them.

**Docs.** The authoring guide's *In Blockbench* section gains *Your own pack* as its first
subsection, since it is the first thing a new author needs, and the settings are listed there.

## 5. The advanced smithing table

**Today.** Everything goes through the vanilla smithing table, and the table is a one-way door. It
puts a part on and it sets a fitting, but it cannot take a part off: there is no ingredient that
means "nothing", and a socket once filled stays filled until another part replaces it. Nor does it
show what it is doing - the result slot holds one item, the preview stand wears only that item, and
a player dressing a whole set works one piece at a time with no view of the four together. And a
piece wearing three parts has three lines of tooltip and nothing else to say which template made
which.

**Change.** A block, `armorpieces:advanced_smithing_table`, crafted from a smithing table, an armor
stand and two iron ingots. Right-click opens a menu with:

- *Four display slots* down the left, one per armor slot, in the order the inventory lists them.
  Whatever is in them is worn by the armor stand in the preview, all at once. A button beside each
  slot selects that piece; the first piece placed selects itself, and the selection follows
  whatever is left when a piece is taken out.
- *The row list* for the selected piece, in a box of its own: one row per socket the piece's armor
  type owns, head to toe in anchor order, and one more under them for the piece's trim. The box is
  always the size of the longest list a piece can have - the chestplate's four sockets and its trim -
  so it does not resize as pieces are picked, and a neck runs out of its left edge into the armor slot
  holding that piece, in the slot's own grey and at its own height, so the box reads as that slot
  opened up - which is what says whose rows these are. Each row is a button that
  works on it, then the part as the socket template carrying it - the same item the creative tab
  holds - then one slot per fitting the part declares, empty or filled, on fixed columns so the parts
  line up down the box. Every filled icon wears a half-size second icon in its corner naming the
  material it is made of, the ingot behind a gold pauldron and the emerald in its stone, which the
  template icon alone never said. A picked row lifts a shade and the picked icon takes a ring.
  Nothing is labelled: the socket's name is on the button that picks it and in the tooltip, which
  also names the part in its material, the fitting and what is set in it, or the trim's pattern.
- *Two slots and two buttons*, template and material, under the stand. They are the smithing table's
  template and addition slots with the selected piece standing in for the base: Apply runs the
  ordinary smithing recipe lookup on those three stacks and writes the result back into the display
  slot, consuming one of each. So a socket template and an ingot put a part on, a fitting template
  and a gem set a stone, a fitting template alone takes the fittings out - and a vanilla trim
  template and an ingot trim the piece, since the table does not know the difference. A recipe a
  pack has turned off (section 2) is off here too, for the same reason. Remove appears once a row or
  a fitting is picked and empties it - a whole part out of its socket, one fitting out of the part
  in it, or the trim off the piece; nothing is refunded, and this is the one place any of the three
  comes off.
- *Where a fitting goes.* The smithing table has nowhere to say which part it means, so its fitting
  recipe routes by the item alone and one gem fills the stone of every part on the piece. This table
  does have somewhere to say it - the picked row - so it narrows the same rule to that socket, and
  to that one fitting when a fitting icon is what is picked. Nothing else changes: the recipe manager
  still decides that a recipe matched. With the piece picked as a whole, which is how it starts, the
  recipe's own routing stands.
- *The armor stand preview*, full height down the right edge beside the inventory, drawn by the same
  layer that draws armor on a player, so parts and fittings show exactly as they will be worn.
  Dragging across it turns the stand.

Nothing about the table is a new system. Apply is the recipe manager; removal is
`ArmorDecorations.without`; the display slots are typed by the item's `equippable` slot the way the
inventory's armor slots are. The menu keeps no block entity: like the smithing table, it hands
everything back when it closes. Buttons travel as vanilla container-button clicks, so no packet is
added. The client cannot run the recipe lookup itself, so the server writes Apply's result into a
hidden slot that syncs like any other and is never drawn: the stand wears it in place of the
selected piece while it is there, so the part, the stone or the trim is seen before it is paid for,
exactly as the smithing table's stand previews its result slot, and Apply is lit while it holds
something.

**Blockbench.** Nothing. The table is a player-facing block, not an authoring tool.

**Check.** In game: place a decorated helmet, take its crest off with the cross and see the stand
lose it; put a socket template and an ingot in and Apply, see the stand gain it; a fitting template
and a gem set the circlet's stone; Apply stays disabled for a combination the smithing table would
refuse (a crest template on boots, a part whose apply recipe is disabled). Closing the menu returns
every stack. The block drops itself, is mined faster with an axe, and shows in the mod's creative
tab.

**Docs.** A *Taking parts off* paragraph under Features, the block in the recipe images, and one
line in the changelog. The mod page is touched at the end of the phase with the rest.
